## 1. Objetivo

Transformar o esqueleto atual do MykytaDu API em uma base determinística, testável, modular e segura antes de implementar funcionalidades de Identity ou Translation.

**Duração-alvo:** três a cinco dias úteis.

## 2. Baseline observado

No planejamento desta sprint, o repositório apresenta:

- aplicação Spring Boot mínima em um único pacote raiz;
- Java 25 configurado e disponível localmente;
- Gradle Wrapper 9.7.1;
- Spring Boot 4.1.1;
- Kotlin 2.3.21 no build, divergente do Kotlin 2.4.10 registrado no documento mestre;
- PostgreSQL `latest` com nomes e credenciais locais genéricos no Compose;
- `application.yaml` contendo somente o nome da aplicação;
- pastas de migrations e recursos sem conteúdo funcional;
- apenas um teste `contextLoads`;
- dependências iniciais de JPA, Flyway, Security, Resource Server, Actuator, Springdoc e Spring Modulith;
- ausência de Testcontainers, MockK, lint, análise estática e cobertura configurados.

Esse baseline é uma fotografia inicial, não evidência de erro ou de compatibilidade. As tarefas da sprint devem validá-lo.

## 4. Restrições

- nenhuma funcionalidade de cadastro, login, sessão ou tradução;
- nenhuma tabela de domínio além dos schemas vazios;
- nenhuma credencial real ou segredo versionado;
- nenhuma migração destrutiva ou geração automática de schema pelo Hibernate;
- nenhuma adoção de microserviço, broker, Redis ou Kubernetes;
- não flexibilizar segurança para fazer testes passarem;
- decisões estruturais divergentes do documento mestre exigem ADR.

## 5. Critérios de aceite

### Toolchain e dependências

- [x] versões estão reconciliadas com o documento mestre ou com ADR aprovado;
- [x] wrapper seleciona Java 25;
- [x] não há versões dinâmicas, snapshots inesperados ou conflitos críticos;
- [x] cada dependência inicial possui responsabilidade conhecida.

### Modularidade

- [x] Spring Modulith reconhece `app`, `api`, `identity`, `translation` e `shared`;
- [x] não existem ciclos entre módulos;
- [x] teste arquitetural reprova uma dependência proibida representativa;
- [x] `shared` não depende de módulos de domínio.

### Banco e configuração

- [x] PostgreSQL 18 inicia e passa no healthcheck;
- [x] Flyway cria apenas os schemas `identity` e `translation`;
- [x] o schema `public` não contém tabelas de negócio;
- [x] Hibernate não cria nem altera o schema;
- [x] testes não dependem de banco manual ou estado compartilhado;
- [x] configurações obrigatórias ausentes produzem erro compreensível.

### HTTP, segurança e observabilidade

- [ ] rota protegida sem credencial retorna `401`;
- [ ] validações e erros inesperados usam `application/problem+json`;
- [ ] erros possuem `code` e `traceId`, sem stack trace exposto;
- [ ] Actuator expõe apenas endpoints aprovados;
- [ ] liveness não depende do banco e readiness reflete sua indisponibilidade;
- [ ] logs não contêm autorização, tokens, credenciais ou payload sensível;
- [ ] métricas HTTP usam rotas normalizadas e labels de cardinalidade controlada.

### Qualidade e operação

- [x] testes unitários, arquiteturais e de integração podem ser identificados separadamente;
- [x] Testcontainers aplica as migrations em PostgreSQL efêmero;
- [ ] ktlint, Detekt e Kover executam localmente e no CI;
- [ ] pipeline bloqueia integração diante de falha em um gate obrigatório;
- [ ] documentação permite preparar, iniciar, testar e resetar o ambiente.
